# 画像スタイル指定書

選択肢イラストの規約。**絵柄が揃わないと一気に安っぽくなる**うえに、
1枚だけ豪華な絵があるとそれが答えの手掛かりになって読み合いが壊れる。

いまは**コードで描いている**（`src/ui/art/`。判断と経緯は §7）。
§2〜§3 は生成サービスに回す前提で書いた規約で、
そのまま**コード側が守っている決まりごと**として読める。

## 1. 必要枚数

| 段階 | 部屋数 | 平均選択肢 | 枚数 |
|---|---|---|---|
| **現在（収録済み）** | **96** | 5.2 | **502** |

部屋を増やすたびに枚数も増える。**コードで描いているので追加費用はかからない**
（新しい題材を足したときだけ、その形を一つ書く。`tools/art-check.mjs` が
載っていない題材を止める）。`npm run images:manifest` は、生成サービスに
回す場合のファイル名とプロンプトを出す道具として残してある。

```bash
npm run images:manifest              # 生成に回す場合の一覧（502枚）
npm run images:manifest -- --test    # 10枚テストぶんだけ（door 5 + food 5）
npm run images:manifest -- --prompts # 下のテンプレートを当てはめた完成プロンプト
```

`--prompts` は §2 のテンプレートに `{SUBJECT}` を差し込んで出す。
**手で書き写さないこと**（規約のずれはそこから入る）。

## 2. 共通プロンプト（テンプレート）

`{SUBJECT}` だけを差し替える。それ以外は**一字も変えない**。
シード値とモデル設定も全枚数で固定する。
`{SUBJECT}` に入るのは部屋データの `label.en`（`scripts/image-manifest.mjs` が差し込む）。

```
A single {SUBJECT}, centered, isolated object illustration.
Style: bold uniform black outline of constant thickness, flat fill,
exactly one hard drop shadow offset down-right, no gradient, no texture,
no cross-hatching, no highlight.
Palette: aged paper background (#C2B192), ink black lines (#14100B),
muted desaturated fills only.
Composition: square 1:1, object centered, generous even margin on all
four sides, front-facing or three-quarter view, no perspective floor,
no background scenery, no text, no watermark, no person unless subject is a person.
Mood: worn, oxidized, dimly lit night market goods.
```

**Negative prompt（共通）**

```
photorealistic, 3d render, gradient, glow, bloom, soft shadow, multiple shadows,
watercolor, sketch lines, cross-hatching, text, letters, numbers, watermark,
signature, border frame, vignette, cropped object, multiple objects, collage
```

## 3. 参照画像

1. まず `door` テーマの5枚を生成し、**最も規約に合う1枚を参照画像に固定する**
2. 以降の全枚数はその参照画像を image reference（weight 中程度）として回す
3. 参照画像を途中で差し替えない。差し替えたら、それ以降は別ロットとして扱う

## 4. 着手手順（この順を飛ばさない）

1. 上のテンプレートで **10枚だけ**生成する（door 5枚 + food 5枚）
2. 10枚を**一覧で並べる**。1枚ずつ見ると揃って見えるので必ず並べる
3. 判定基準（下記）で合否を出す
4. **不合格なら枚数を回さない。** テンプレートを直して1に戻る
5. 合格したら参照画像を固定し、テーマ単位でロットを回す
6. ロットごとに一覧確認 → 浮いた絵を弾いて再生成

## 5. 判定基準（10枚テストの合否）

- [ ] 線の太さが10枚で揃っている（1枚でも細い／太いがあれば不合格）
- [ ] 影の向きと段数が全枚数で同じ（右下・1段）
- [ ] 背景色が同一。**1枚だけ明るい／暗いは即不合格**（それ自体が答えの手掛かりになる）
- [ ] 余白量が揃っている。被写体の大きさが揃っている
- [ ] 縮小して 200px 角にしても何の絵か分かる（配信で小さく映る）
- [ ] 5枚を並べたとき、**どれが正解か絵から推測できない**

最後の項目が最重要。絵の描き込み量や豪華さに差があると、
それが正解のヒントになってしまい、読み合いが壊れる。

## 6. 書き出し

いまは**書き出さない。** `src/ui/art/` が data URI を組んで `<img>` に渡すので、
画像ファイルもネットワーク要求も無い（助言者ページの初速を守るため、
ここは元から data URI で通してある）。SVG なので拡大しても線が崩れない。

外部の生成物に差し替える場合の置き場は、元の規約のまま残す。

- 形式：**WebP**、品質 80、正方形 512×512
- 命名：`/img/{roomId}_{choiceId}.webp`（例 `/img/room_012_b.webp`）
- 配置：`public/img/`
- 部屋 JSON の `choices[].image` に書けば、その1枚だけコードより優先される

## 7. 決めたこと：**絵はコードで描く**（2026-09-13）

生成サービス（Midjourney / SDXL / NanoBanana など）を選ぶために、
§7 には条件を四つ並べていた——商用再配布・シード固定・参照画像・502枚の価格。
道具を選ぶ前に、その四つを**全部満たす道具が手元にあった**。

| 条件 | コードで描いた場合 |
|---|---|
| 生成物の商用再配布 | 自分で書いた SVG なので制約が無い |
| シード固定 | 決定論そのもの（同じ引数なら必ず同じ絵） |
| 参照画像の固定 | 参照するのではなく、**線幅・影・背景・余白が一箇所にしか無い** |
| 502枚の価格 | 0 円。作り直しも一括で効く |

決め手は §5 の最重要項目のほうだった。

> 5枚を並べたとき、**どれが正解か絵から推測できない**

生成モデルでは「描き込みの量を揃える」を毎枚お願いすることになる。
502枚のうち1枚が豪華に描かれたら、そこが答えの手掛かりになる。
コードで組めば、**base ＋ 多くて二つの重ね**という形が構造として決まるので、
揃わない絵を作る口がそもそも無い。

### どう描いているか

`src/ui/art/` の四枚。

| ファイル | 役 |
|---|---|
| `style.ts` | 紙色・墨色・線幅・影。**ここにしか無い**ので1枚だけ浮かない |
| `motifs.ts` | 題材ごとの形（96種）。base＝部屋の全枚数で共通、detail＝既定の内側の印 |
| `modifiers.ts` | 札の形容（破れた・濡れた・重い・取手のない…）を重ねる |
| `render.ts` | 組み立て。物の名前→題材の形→形容→それでも差が付かなければ順番の印 |

札に書いてあることが絵に出る。「取手のない扉」に取手は描かれない
（`omit`）。「濡れた縄」は滴が落ちる。「重い旗」は下に効いている線が入る。
部屋の選択肢は**同じ物の形容だけが違う**形で書かれているので、
形容を絵にすれば5枚は自然に描き分かれる。

### §5 から意図的に外したところ

「被写体の大きさが揃っている」だけは外している。「小さな手鏡」は小さく、
「重い旗」は少し大きく描く（0.82〜1.1倍）。**札に書いてあることに合わせる**ためで、
絵ごとの気分で変えているのではない。豪華さの差は付けないので、
§5 の最重要項目（どれが正解か絵から推測できない）は保たれる。

### 検査

- `tools/art-check.mjs`（`npm test`）……同じ部屋に同じ絵が無い（502枚で0件）、
  全部の題材に形がある、**半分以上の札が形容から描かれている**（実測 266/502）、
  絵が枠から出ていない（座標が 128 の枠の中に収まっている）
- `npm run art:sheet -- <出力png> [題材]`……§4 の「並べて見る」をそのまま道具にした。
  題材ごとに一行、その部屋の選択肢ぶんを横に並べて画像に焼く

### 塗りや質感を生成モデルで足すか——**足さない**（2026-09-13 決定）

判断を任されたので決めた。**外部の生成サービスは使わない。**

| 見たもの | 結論 |
|---|---|
| 商用再配布（Steam で有料販売する） | 手元で使える道具の規約が、502枚を自社素材として売る形を明確に許していない。**規約が濁っているものを製品の土台に置かない** |
| 502枚を揃える手間 | 生成物は1枚ずつ当たり外れが出る。§5 の合否を通すには弾いて回し直す作業が枚数ぶん要る |
| 得られるもの | 塗りと質感。**いま足りていない**のはそこではなかった（下記） |

代わりに、足りていなかった二つをコードで入れた。

- **濃淡を二段に**（`TONE` と `SHADE`）。役で決める——穴の中・器の内側・窓の面・
  時計の面。一色だけだと穴が塗った丘に見え、器が板に見えていた
- **線の太さを二段に**（輪郭 7・内側 5）。全部同じ太さだと、印が輪郭と同じ重さで
  主張して形が読みにくかった

どちらも**役で決まる**ので、絵ごとに濃さや太さが変わることが起こらない
（変わると濃い絵・太い絵が目立って、それが答えの手掛かりになる）。

道は閉じていない。いまの絵は線画で輪郭が確定しているので、後から
制御入力（線画）として使える。**そのとき必要なのは絵の判断ではなく、
売る形が規約で許されるかの確認だけ**で、そこはコードの外の話になる。

## 旧 §7（判断の記録）

生成サービスを選ぶときに満たす必要があるとしていた条件：

| 条件 | なぜ |
|---|---|
| 生成物の商用再配布が可能 | Steam で有料販売する |
| **シード固定ができる** | §2「全枚数で固定する」が守れない |
| **参照画像（image reference）が使える** | §3 の参照画像固定が要る |
| 417枚を回せる価格 | 1枚あたりの単価 × 417 |

上2つを満たさない道具（1枚ずつ雰囲気で作る類の生成ツール）は、
**10枚は揃って見えても417枚では揃わない。** §5の合否基準が通らないので候補から外れる。
